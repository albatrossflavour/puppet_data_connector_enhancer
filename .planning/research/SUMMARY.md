# Project Research Summary

**Project:** Puppet Data Connector Enhancer - Self-Service Graphs
**Domain:** Puppet infrastructure metrics exporter with self-service observability
**Researched:** 2026-04-05
**Confidence:** MEDIUM (codebase analysis HIGH confidence; Grafana schema and PE API details MEDIUM)

## Executive Summary

This is a brownfield Puppet module that exports infrastructure metrics to Prometheus via the
node_exporter textfile collector. The milestone adds three new capabilities: self-service custom
metrics from PQL queries defined in YAML, auto-generated Grafana dashboards per metric definition,
and expanded self-monitoring of the exporter itself. The technology stack is fully constrained by
the Puppet Enterprise runtime (PE-embedded Ruby, Puppet DSL, EPP templates), so there are no
meaningful tech choices to make. Every new feature must work within that constraint with zero new
dependencies.

The recommended approach is to treat the custom metrics YAML schema as the single source of
truth for both collection and visualisation. One YAML definition produces both the Prometheus
metric and the Grafana dashboard. Dashboard generation should happen at Puppet compile time (as a
custom Puppet function producing managed `file` resources), not at collection runtime. This keeps
dashboard files Puppet-managed with proper checksums and separates two concerns that have different
change frequencies. The existing `parse_csv` function in the module establishes the pattern; a
`generate_dashboards` function fits naturally alongside it.

The main risks are cardinality explosion from unbounded PQL queries, metric name collisions
between user-defined and built-in metrics, and YAML injection from PQL queries containing
special characters. All three are detectable at Puppet compile time or YAML parse time, before
anything reaches Prometheus. Address these in the custom metrics phase. Defer cardinality
controls, dashboard customisation options, and anything that couples the module to the Grafana
HTTP API.

## Key Findings

### Recommended Stack

No new technology is needed. The full capability set is achievable with PE-embedded Ruby stdlib
(`json`, `yaml`, `fileutils`, `timeout`) and Puppet DSL. Dashboard JSON is generated by building
Ruby hash structures and calling `JSON.pretty_generate`, which is both simpler and safer than any
template approach. The existing codebase is already correct on atomic file writes, Prometheus
exposition format, and retry-with-backoff. The patterns to follow are already in the codebase.

**Core technologies:**

- Ruby (PE-embedded, 2.7-3.2): Collection script runtime. No new gems. Stdlib only.
- Puppet DSL / EPP templates: Module manifests and config file generation. Already in use.
- `JSON.pretty_generate` (Ruby stdlib): Dashboard generation via hash-to-JSON. No ERB for JSON.
- Prometheus exposition format 0.0.4: Metric output. Already correctly implemented.
- Grafana dashboard JSON schemaVersion 41: Target for generated dashboards (Grafana 10-11).
- Custom Puppet function (`generate_dashboards`): Compile-time dashboard generation. Follows
  existing `parse_csv` pattern.

See [STACK.md](.planning/research/STACK.md) for full version compatibility matrix and metric
name validation regexes.

### Expected Features

**Must have (table stakes):**

- HELP/TYPE headers for all metrics, including custom ones. Prometheus tooling assumes them.
- YAML config validation with actionable error messages. The error message is the product.
- Metric naming consistency enforced via validation. Names must start with `puppet_custom_` prefix.
- Orchestrator job and plan run metrics. Already implemented on `feature/orchestrator-metrics`.
- Node classification group metrics. Already on `feature/orchestrator-metrics` branch.
- Documentation with copy-paste examples for each PQL endpoint type.

**Should have (differentiators):**

- PQL-to-metric pipeline via YAML config. The headline feature. Drops time from "found useful
  data" to "graphed it" from days to minutes.
- Auto-generated Grafana dashboards from metric definitions. Single source of truth: one YAML
  definition, one metric, one dashboard. Panel type inferred from metric shape.
- Self-monitoring metrics (API call counts/durations, collection success rates, process CPU/RSS).
  Separates production-grade tooling from scripts.
- Example Prometheus alert rules alongside dashboards. Low effort, saves users hours of
  threshold-guessing.

**Defer to v2:**

- Cardinality warnings in YAML validation. Document the concern, let users self-regulate.
- Dashboard customisation options in YAML. Users can edit generated JSON directly.
- Direct Grafana API provisioning. Wrong tool, wrong coupling, breaks air-gapped environments.
- Multi-format output (InfluxDB, Datadog). Fragments codebase for a tiny audience.

See [FEATURES.md](.planning/research/FEATURES.md) for the anti-features list, which is equally
important.

### Architecture Approach

The new features slot into the existing architecture as three subsystems that share the same
data-flow shape: config in, outputs written to disk. Custom metrics collection extends the
existing `PrometheusMetricsGenerator` class. Dashboard generation runs at compile time via a
new Puppet function. Self-monitoring wraps the existing collection infrastructure. The critical
path is: stabilise the custom metrics YAML schema first, because both the dashboard generator
and the alert rules reference it.

**Major components:**

1. `init.pp` (Manifest) -- orchestrates file deployment, validates params, manages systemd units
2. Custom Queries YAML Config -- single source of truth for collection behaviour and dashboard layout
3. `PrometheusMetricsGenerator` (Ruby) -- collects metrics from PuppetDB, Orchestrator, Classifier APIs
4. `generate_dashboards` Puppet function -- compile-time dashboard JSON generation from metric definitions
5. Self-monitoring subsystem -- extends existing `add_exporter_health_metrics` with per-endpoint stats

See [ARCHITECTURE.md](.planning/research/ARCHITECTURE.md) for the component boundary table, data
flow diagrams, and panel type inference rules.

### Critical Pitfalls

1. **Cardinality explosion from unbounded PQL queries** -- Add `max_rows` per metric (default 500)
   and a global custom series budget. One badly-scoped query against 5,000 nodes produces 5,000
   new time series. Implement in the custom metrics phase, not deferred.

2. **Metric name collisions with built-in metrics** -- Require `puppet_custom_` prefix for all
   user-defined metrics. Maintain a reserved-prefix set. Validate at YAML parse time and fail
   loudly. Silent deduplication dropping custom rows is worse than a parse error.

3. **YAML injection from PQL queries** -- PQL queries routinely contain colons, quotes, and
   hashes. The current EPP template wraps values in double-quotes without escaping internal quotes.
   Fix with `YAML.dump` from structured data or Puppet's `to_yaml` function. This is an existing
   bug in the partial implementation.

4. **Grafana datasource UID mismatch** -- Generated dashboards must use the
   `${DS_PROMETHEUS}` variable pattern for all datasource references, not hardcoded UIDs. Every
   Grafana installation has a different UID for the same datasource.

5. **Dashboard JSON file proliferation** -- Default to a single "Custom Metrics" dashboard with
   one panel per definition, not one dashboard per metric. Twenty custom metrics should not mean
   twenty dashboard files.

See [PITFALLS.md](.planning/research/PITFALLS.md) for the full audit including moderate pitfalls
(YAML injection, datasource mismatch, observer effect in self-monitoring) and codebase-specific
concerns from CONCERNS.md.

## Implications for Roadmap

Based on research, the dependency graph drives the phase order. The custom metrics schema must
be stable before dashboards can be generated. Orchestrator metrics are already implemented and
can be merged independently. Self-monitoring wraps everything else so it comes late.

### Phase 1: Orchestrator and Classifier Metrics Merge

**Rationale:** The `feature/orchestrator-metrics` branch is already implemented. Merge, test,
validate. Low marginal effort, high operational value. Independent of all other new work.

**Delivers:** Orchestrator job/plan metrics, node group classification metrics, PE infrastructure
visibility.

**Addresses:** Orchestrator job metrics and node classification metrics (both table stakes).

**Avoids:** Pitfall 9 (API auth differences). Review auth handling for RBAC token vs SSL cert
patterns. Test against PE 2023.x and 2025.x.

**Research flag:** Review the feature branch implementation before this phase. Auth handling for
the Orchestrator API needs validation. Otherwise standard Puppet patterns.

### Phase 2: Custom Metrics YAML -- Schema, Validation, and Collection

**Rationale:** This is the foundation. Dashboard generation, alert rules, and self-monitoring all
depend on this being solid and the schema being stable. Address the known defects (YAML injection,
missing validation) here.

**Delivers:** Working `puppet_custom_*` metrics from user-defined YAML. Validated schema with
clear error messages. Metric name validation and collision detection.

**Addresses:** PQL-to-metric pipeline (headline differentiator), YAML config validation (table
stakes), metric naming consistency (table stakes).

**Avoids:** Pitfall 1 (cardinality, add `max_rows`), Pitfall 3 (name collisions, require
`puppet_custom_` prefix), Pitfall 5 (YAML injection, fix EPP template), Pitfall 12 (metric name
regex validation).

**Research flag:** Standard patterns. No additional research needed. The regex validation,
dot-path extraction, and YAML-safe escaping approaches are all established.

### Phase 3: Self-Monitoring Expansion

**Rationale:** Instrument the collection script with per-endpoint API call counts, durations, and
process resource usage. Extends the existing `add_exporter_health_metrics`. Can proceed once
Phase 2 metrics structure is stable, so the instrumentation wraps all collectors.

**Delivers:** `puppet_exporter_api_requests_total`, `puppet_exporter_api_duration_seconds`,
`puppet_exporter_collection_duration_seconds`, `puppet_exporter_process_cpu_seconds_total`,
`puppet_exporter_process_resident_memory_bytes`.

**Addresses:** Self-monitoring differentiator. Also surfaces Pitfall 2 (slow query detection via
per-custom-metric timing).

**Avoids:** Pitfall 7 (observer effect -- measure coarsely, not per-call).

**Research flag:** Well-established Prometheus exporter conventions. No additional research needed.

### Phase 4: Auto-Generated Grafana Dashboards

**Rationale:** The most complex feature and the most dependent. Requires stable metric definitions
(Phase 2) and a working example of what the metrics look like (Phase 3). Implement as a custom
Puppet function (`generate_dashboards`) following the existing `parse_csv` pattern.

**Delivers:** Grafana dashboard JSON files per custom metric definition (or a combined dashboard).
`${DS_PROMETHEUS}` variable pattern throughout. Conservative schemaVersion targeting Grafana 10+.

**Addresses:** Auto-generated Grafana dashboards (headline differentiator).

**Avoids:** Pitfall 4 (schema drift -- conservative schemaVersion, stable panel types only),
Pitfall 6 (datasource mismatch -- use variable pattern), Pitfall 11 (file proliferation --
default to single combined dashboard).

**Research flag:** Verify the exact `schemaVersion` in use against the Grafana version deployed
in the target environment. The research targets schemaVersion 41 (Grafana 11) but notes that
Grafana schema field names should be validated against the actual running version.

### Phase 5: Example Alert Rules and Documentation

**Rationale:** Documentation-like work that references all the metrics defined in earlier phases.
Ship example `.rules.yml` files covering collection failures, node count changes, patch compliance
drops, and orchestrator failures. Write documentation last because it documents everything above.

**Delivers:** Example Prometheus alert rules (differentiator), updated README with copy-paste
examples for each PQL endpoint type (table stakes).

**Addresses:** Alert rules differentiator, documentation table stakes.

**Avoids:** Pitfall 10 (PQL version notes), Pitfall 1 (cardinality guidelines in docs).

**Research flag:** Standard documentation work. No research phase needed.

### Phase Ordering Rationale

- Phase 1 is independent of everything else and is mostly done. Merge first to clear the branch.
- Phase 2 is the critical path. The YAML schema is the contract that Phases 4 and 5 depend on.
  Do not start dashboard generation before the metric definition schema is stable.
- Phase 3 can overlap with late Phase 2 work, but gains more value once all collectors are in
  place (after Phase 1 merge).
- Phase 4 is last among the feature work because it depends on stable metric definitions, working
  collection, and knowing what the metrics actually look like in practice.
- Phase 5 is always last. Documentation written before implementation is speculation.

### Research Flags

Phases likely needing deeper research during planning:

- **Phase 1 (Orchestrator merge):** Review auth handling on the feature branch before planning
  the merge. The Orchestrator API's RBAC token vs SSL cert requirements differ by PE version.
- **Phase 4 (Dashboard generation):** Verify the exact Grafana schemaVersion deployed in the
  target environment. The research is based on codebase analysis of existing dashboards; the
  actual Grafana version should be confirmed.

Phases with standard patterns (skip research phase):

- **Phase 2 (Custom metrics):** All patterns established. Prometheus naming conventions, YAML
  validation, dot-path extraction are well-documented and already partially implemented.
- **Phase 3 (Self-monitoring):** Standard Prometheus exporter pattern. Existing codebase already
  implements the base case correctly.
- **Phase 5 (Docs/alerts):** Writing work. No research needed.

### Gaps to Address

- **Grafana schemaVersion in target environment:** Research targets schemaVersion 41 (Grafana
  11.x). Confirm the actual Grafana version in use. Adjust the generator target if the
  environment is on Grafana 9.x or 10.x.
- **Orchestrator API auth requirements by PE version:** The feature branch implementation should
  be reviewed for consistency with PE 2023.x and PE 2025.x auth patterns before the Phase 1 merge.
- **`ssl_verify_none` remediation:** CONCERNS.md flags SSL verification disabled. Adding more
  API endpoints (Orchestrator, Classifier) before fixing this elevates the risk. Consider whether
  this blocks Phase 1 or is acceptable as a follow-on item.
- **PQL query performance characterisation:** No benchmark data exists for the expected query
  execution times in large estates. The per-query timeout default (suggested 10 seconds) is a
  reasonable starting point but should be validated against actual PuppetDB query performance.
