<objective>
Create the CLI metric builder tool that guides users through adding custom metric definitions to their YAML config file.

Purpose: Users currently have to hand-craft YAML definitions, risking syntax errors and invalid configurations. The CLI tool (D-19 through D-24) validates inputs using the same rules as the runtime engine, shows a preview of the Prometheus output, and can query PuppetDB live to show real data. This dramatically reduces the copy/paste-from-chatbot friction.

Output: New EPP template generating the CLI Ruby script. Updated init.pp with file resource for deployment.
</objective>

Create a new EPP template `templates/puppet_custom_metric_builder.epp` that generates a Ruby CLI script. Per D-19 through D-24.

**EPP parameter block:**
```epp
<%- | String $custom_queries_file,
      String $puppet_server,
      Integer $custom_queries_row_limit,
| -%>
```

**Script structure:**

The generated script must use the PE Ruby shebang `#!/opt/puppetlabs/puppet/bin/ruby` and follow the same `# frozen_string_literal: true` convention. Required libraries: `json`, `net/http`, `uri`, `yaml`, `set`, `openssl`, `optparse`, `fileutils`.

Create a `CustomMetricBuilder` class with these responsibilities:

**1. Shared validation logic (D-20):**
Copy the exact same validation constants from the main EPP template: `BUILTIN_METRIC_PREFIXES`, `VALID_ENDPOINT_TYPES`, `VALID_METRIC_TYPES`, `PROMETHEUS_NAME_PATTERN`, `PROMETHEUS_LABEL_PATTERN`, `DANGEROUS_PQL_PATTERNS`, `ISO8601_TIMESTAMP_PATTERN`. Copy the validation methods: `validate_single_definition`, `validate_pql_query`, `sanitise_pql_timestamp`. This ensures single source of truth per D-20 — both files are generated from the same EPP compilation, so the constants are identical at deploy time.

**2. CLI argument parsing (D-24):**
Use `OptionParser` with these flags:
- `--name NAME` — metric name
- `--endpoint TYPE` — endpoint type (fact/pql/resource/inventory/nodes)
- `--type TYPE` — Prometheus metric type (gauge/counter/etc.)
- `--help-text TEXT` — HELP string (avoid `--help` conflict with OptionParser)
- `--pql-query QUERY` — PQL query string
- `--fact-name NAME` — fact name for fact endpoint
- `--resource-type TYPE` — resource type for resource endpoint
- `--labels LABELS` — comma-separated key=path pairs (e.g. `certname=certname,os=facts.os.name`)
- `--value-path PATH` — dot-path to numeric value field
- `--row-limit N` — per-metric row limit (default: `<%= $custom_queries_row_limit %>`)
- `--filter FILTER` — PuppetDB query filter
- `--preview-only` — show preview without writing to file
- `--live-preview` — query PuppetDB for real sample data (D-22)
- `--config-file PATH` — YAML config file path (default: `<%= $custom_queries_file %>`)

If no flags are provided (or required flags are missing), enter interactive mode (D-24).

**3. Interactive mode (D-24):**
Prompt for each required field in sequence:
1. Metric name (with puppet_custom_ prefix guidance)
2. Endpoint type (show numbered options)
3. Endpoint-specific fields (pql_query, fact_name, resource_type based on choice)
4. Prometheus metric type (show numbered options)
5. HELP text description
6. Labels (ask if labels needed, then prompt key=path pairs until done)
7. Value field path (or skip for count-style metrics)
8. Row limit (show default, allow override or 0 for unlimited)
9. Filter (optional)

Validate each input as it is entered. Show errors immediately and re-prompt.

**4. Preview generation (D-21):**
Method `generate_preview(defn)` that outputs:
```
# HELP puppet_custom_example Example metric description
# TYPE puppet_custom_example gauge
puppet_custom_example{certname="<certname>",os="<os>"} <value>
puppet_custom_example{certname="<certname>",os="<os>"} <value>
```

When labels are defined, show placeholder label values in angle brackets. When no labels, show just the metric name and a placeholder value.

**5. Live preview (D-22):**
Method `live_preview(defn)` that:
- Reads SSL cert/key/CA from the same paths as the main script: `/etc/puppetlabs/puppet/ssl/certs/<%= $puppet_server %>.pem`, `/etc/puppetlabs/puppet/ssl/private_keys/<%= $puppet_server %>.pem`, `/etc/puppetlabs/puppet/ssl/certs/ca.pem`
- Makes an HTTPS request to PuppetDB using the same `fetch_json_from_puppetdb` pattern (SSL client cert auth)
- Fetches up to 3 sample rows (limit=3)
- Renders preview using actual data from the response
- Handles connection errors gracefully with a clear message

**6. YAML writing:**
Method `write_to_config(defn, config_file)` that:
- Reads existing YAML file if it exists (creating `{ 'metrics' => [] }` if not)
- Loads existing definitions to check for duplicate names
- Appends the new definition to the metrics array
- Writes back using `YAML.dump` with clean formatting
- Reports success with the file path

**7. Main flow:**
```ruby
builder = CustomMetricBuilder.new
defn = builder.collect_inputs  # from flags or interactive
errors = builder.validate(defn)
if errors.any?
  errors.each { |e| STDERR.puts "ERROR: #{e}" }
  exit 1
end
builder.show_preview(defn)
builder.show_live_preview(defn) if builder.live_preview?
unless builder.preview_only?
  builder.write_to_config(defn)
  puts "Metric definition written to #{builder.config_file}"
end
```

**Ruby conventions to follow:**
- `# frozen_string_literal: true` after shebang
- Use `%r{}` for regexps, `%` for format strings
- Trailing commas on multiline arrays/hashes
- Methods use `snake_case`
- Constants use `SCREAMING_SNAKE_CASE`
- Max line length 200
